# Architecture decisions

Each decision records what was chosen, what it costs, and what would justify
revisiting it. A decision with no stated cost has not been thought about
carefully enough.

---

## ADR-0001 — The product is a platform; NuESheba is configuration

**Decision.** Build a reusable Business OS. NuESheba is
`configs/nuesheba/business.json`. No file under `apps/` or `packages/` names it.

**Why.** The alternative — build NuESheba, extract a platform later — is the
more common path and it rarely completes. Client-specific assumptions spread
into shared code faster than anyone extracts them, and by the time a second
client arrives the "extraction" is a rewrite. Building the seam first costs
something now; building it later usually costs everything.

**Cost.** Roughly 20-30% more work on the first client. Every feature must be
expressed generically even when only one business needs it, and a configuration
indirection sits between the code and the thing it does.

**Revisit if.** Twelve months pass with exactly one tenant. At that point the
generality is speculative and should be collapsed.

**Naming.** The scope is `@bos/*` and the product is called "Business OS" in
docs. This is deliberately provisional — the name is a find-and-replace away.
`Businessistic Core` fits the existing `-istic` family (WPistic, Chatbotistic,
Licenseistic, Memberistic) and is the recommendation, but naming is the owner's
call and nothing waits on it.

## ADR-0002 — WordPress is an optional content source, never the system

**Decision.** `@bos/content` defines `ContentProvider`. `apps/site` depends on
that interface only. WordPress is one implementation; the internal CMS is the
default.

**Why.** WordPress's REST API is genuinely good at what it is for: editorial
content and media, with an editing experience people already know. What it is
not is a business data model. Putting a CRM, scheduling and automation into
`wp_postmeta` means every query is a join against a key-value table, every
integration is a plugin you do not control, and every upgrade is a risk
assessment.

Keeping it behind an interface means the editorial convenience stays available
and the dependency stays removable.

**Cost.** An abstraction layer that, for a client who will never leave
WordPress, does nothing. Three implementations to keep honest instead of one.

**Also decided.** Elementor is not used as a headless page builder. Its output
is presentational markup, and consuming it would put layout decisions in a tool
that knows nothing about the design system. If WordPress editing is required,
content is authored as structured blocks that map to registered sections.

## ADR-0003 — PostgreSQL with row-level security for tenancy

**Decision.** One database, one schema, `workspace_id` on every tenant-scoped
table, RLS enabled and forced. The application connects as `bos_app`
(`NOSUPERUSER`, `NOBYPASSRLS`, DML only).

**Why.** Schema-per-tenant multiplies migration risk by tenant count.
Application-level `WHERE workspace_id = ?` works right up until the one query
that forgets it. RLS makes the tenant predicate a property of the database, and
makes the failure mode "sees nothing" rather than "sees everything".

**Cost.** Every query must run inside `withWorkspace()`. Cross-tenant jobs need
a deliberate, greppable escape hatch. Debugging a query that returns nothing
requires remembering RLS exists.

**The part that is easy to get wrong.** RLS does not apply to superusers, to
`BYPASSRLS` roles, or — without `FORCE` — to the table owner. Policies can be
perfect and every boundary still open, purely because `DATABASE_URL` points at
the wrong role. This was caught during implementation: the first isolation test
passed trivially because the connection was a superuser. `sql/grants.sql`
provisions the least-privilege role, `pnpm db:migrate` re-applies it, and
`tests/rls.test.ts` asserts both directions — that `bos_app` sees one tenant,
_and_ that a superuser sees everything.

## ADR-0004 — Drizzle, with SQL generated from TypeScript

**Decision.** Schema in TypeScript (`packages/database/src/schema/`), SQL
migrations generated by drizzle-kit and committed. CI fails if the two diverge.

**Why.** Hand-writing both a TypeScript model and SQL DDL guarantees drift.
Generating types from SQL means the schema is not reviewable as code.
Generating SQL from types keeps one source of truth and produces a committed,
reviewable artefact.

**Cost.** Anything drizzle-kit cannot express — RLS policies, roles, partial
index predicates in unusual shapes — is hand-written SQL applied separately.
That split is real and has to be documented, which is why `sql/` exists.

## ADR-0005 — Workspace packages ship TypeScript source

**Decision.** Internal packages have no build step. `main` points at
`src/index.ts`, and consumers compile them: Next.js via `transpilePackages`,
the API via esbuild, tests via Node's type-stripping.

**Why.** A build step per package means build ordering, stale artefacts, and a
watch mode that is subtly wrong. Bundlers already compile TypeScript.

**Cost, and the two things it forces.** Relative imports use explicit `.ts`
extensions (with `rewriteRelativeImportExtensions` for the emit case), because
Node's type-stripping does not remap `.js` to `.ts`. And **constructor
parameter properties are banned** — strip-only mode rejects them, since they
emit runtime code. Both constraints were found by running the code, not by
reading about them.

## ADR-0006 — The public site and the dashboard are separate applications

**Decision.** `apps/site` and `apps/dashboard` are two Next.js builds, not two
route groups in one.

**Why.** The site's JavaScript budget is a user-experience and
ranking-adjacent concern. The dashboard's is not — it is an authenticated tool
where a data grid and a charting library are worth their weight. Sharing a
build means permanently fighting to keep admin dependencies out of a landing
page, and that is a fight you lose gradually and invisibly.

**Cost.** Two builds, two deploys, and shared UI must live in a package rather
than a directory.

## ADR-0007 — Hybrid deployment: origin for the API, edge for spiky work

**Decision.** Next.js apps and the Fastify API run on managed Node hosting next
to Postgres and Redis. Cloudflare handles DNS, CDN, WAF, analytics ingestion,
webhook receipt, queues and scheduled jobs.

**Why.** The API needs transactions, RLS session context and a warm connection
pool. Moving it to Workers trades a real database session for Hyperdrive plus
careful reasoning about connection reuse, and buys nothing a user would feel —
the API is not on a latency-critical path.

Analytics ingestion and webhook receipt are the opposite: high volume, tiny
payloads, no transaction, and genuinely better close to the client. A traffic
spike should not consume origin capacity that a form submission needs.

**Cost.** Two runtimes, two deployment mechanisms, and code that must be honest
about which environment it targets.

**Revisit if.** Global read latency becomes a measured problem rather than an
assumed one.

## ADR-0008 — Sections are a registry, not a page builder

**Decision.** A page is an ordered list of `{ type, variant, props }`, each
validated by its type's schema. Renderers live in `apps/site`. Drag-and-drop
composition can come later; arbitrary layout cannot.

**Why.** A full visual builder is a large product in its own right, and the
thing it buys — editors positioning elements freely — is the thing that
destroys design consistency across a hundred client sites. Structured sections
give editorial freedom over _content_ while the design system keeps control of
_presentation_.

The second benefit is analytical: because sections are data, "which service
pages have no FAQ section?" is a query. Against stored HTML it is a scraping
exercise.

**Cost.** A new visual arrangement needs a developer. Editors accustomed to
Elementor will find this more restrictive, and that is the intended trade.

## ADR-0009 — A transactional outbox for domain events

**Decision.** Events are written to `event_outbox` in the same transaction as
the change that caused them. A dispatcher publishes to the queue and marks them
sent.

**Why.** Publishing to a queue inside a transaction is a distributed-commit
problem in disguise: publish before commit and you announce a lead that rolled
back; publish after and a crash in between loses it silently. The outbox makes
the event and the change atomic, and moves the failure to a retryable place.

**Cost.** A dispatcher to run and monitor. At-least-once delivery, so every
consumer must be idempotent — which is why `idempotency_key` is a required
column on `messages` and on the outbox itself.

---

## ADR-0010 — Automation definitions are versioned data

**Decision.** Automations are stored as validated JSON. Editing one creates a
new version. A run pins the version it started on.

**Why.** Sequences run for days. Without versioning, editing a nurture sequence
changes what a customer receives halfway through it, in a way nobody observes
and nobody can reconstruct afterwards.

**Cost.** More storage, and reasoning about which version a run is on when
debugging. Old versions can never be hard-deleted while runs reference them.

## ADR-0011 — Structured data is generated from the entity graph

**Decision.** `seo_entities` and `seo_entity_relations` hold the business's
knowledge graph. JSON-LD is a projection of it, plus what the page actually
renders. `content_entities` records which entities a page is about.

**Why.** Hand-written JSON-LD per page drifts from the page it describes within
about two content edits. Generating it from maintained structured data keeps
`@id` values stable across pages — so the Organization on the contact page and
the one on a service page are recognisably one entity — and makes the "only
emit schema matching visible content" rule mechanically enforceable rather than
a convention someone remembers.

**Cost.** Entities must be maintained, which is real editorial work. The
generator is more complex than a template.

## ADR-0012 — First-party analytics, no cookies, no raw IPs

**Decision.** Collect events on our own domain via the edge Worker. Sessions
are identified by a daily-rotating salted hash of coarse signals. No cookie is
set and no raw IP is stored.

**Why.** Joining a page view to a lead to revenue is the whole reason to have
analytics, and third-party tags cannot do it. Doing collection ourselves also
removes the consent-banner and ad-blocker problems that make third-party data
unreliable in the first place.

The privacy properties are structural rather than configured: a rotating hash
cannot be reversed to an address, and the same person on two days is not
linkable.

**Cost.** Returning visitors are not identified across days until they identify
themselves through a form. Cross-device attribution is not available. Both are
accepted — the alternative is a consent banner and worse data.

## ADR-0013 — Modules gate routes, not responses

**Decision.** The API mounts a module's routes only when the workspace has that
module enabled.

**Why.** A 403 from a route that exists still exposes the surface, still needs
its handler maintained, and still has to be reasoned about in security review.
A route that was never mounted has none of those properties.

**Cost.** The route table depends on tenant state, so "what endpoints exist?"
is answered per workspace. Integration tests must mount modules explicitly.

## ADR-0014 — The public site renders per request from cached data

**Supersedes the caching half of ADR-0007.** The topology is unchanged; what
the site caches is not.

**Decision.** Public pages render on every request. What is cached is the
_content data_ behind them — tagged per path, revalidated on publish — rather
than the rendered HTML.

**Why.** The site sends a nonce-based Content Security Policy, and a nonce must
differ per response. A statically generated or full-page-cached document
carries whichever nonce it was generated with, so serving it to every visitor
makes the policy decorative: an injected inline script would carry the same
nonce as the legitimate ones.

The obvious alternative — full static generation with `script-src 'unsafe-inline'`
— is a strictly worse trade. Inline script is the thing a CSP exists to stop,
and the page is fast either way: with the content already in memory, a render
is sub-millisecond work. The 200ms was always the round trip to the API, and
that is what the tag-based cache removes.

**Why not `unsafe-inline` with hashes.** Hashes work for a fixed set of inline
scripts. Next's hydration payload differs per page and per build, so the hash
set would have to be computed at build time for every route and would break on
any change to the data — which is every publish.

**Cost.** The origin does work on every request rather than serving a file.
That work is a React render with no I/O, and the CDN still absorbs static
assets. A publish invalidates one page's data rather than purging the zone, so
the cost of an edit is one page's worth of cache, not the whole site's.

## ADR-0015 — Every route declares how it is protected, and the boot enforces it

**Decision.** Every Fastify route carries a `bosAccess` config saying whether it
is public, internal, authenticated, or requires a named permission. An assertion
in `onReady` refuses to listen if any route does not.

**Why.** ADR-0013 removes whole modules from the route table, which is the
right coarse control. It does nothing about the individual route somebody adds
next week and forgets to protect — and the failure mode there is silent, because
an unprotected endpoint behaves perfectly until somebody finds it.

Making the classification mandatory turns that from a review question into a
boot failure with the method and path in the message. `public` is a positive
assertion with a written reason, not the absence of one, so a reviewer sees the
decision in the diff.

**Cost.** Four extra lines per route, and a small amount of ceremony around
Fastify plugins that register their own routes — the CORS preflight responder
is exempted by name, which is itself a line somebody had to write and justify.

## ADR-0016 — Cross-tenant resources answer 404, never 403

**Decision.** A request for a resource in another workspace returns 404, with
the same body as a resource that does not exist.

**Why.** A 403 confirms the identifier is real. Given an endpoint that
distinguishes them, an attacker can enumerate another tenant's records one
guess at a time without ever reading one — which is enough to learn how many
customers a competitor has, or whether a particular person is one of them.

It is also the honest answer. Row-level security scopes the query to the
caller's workspace, so the row genuinely is not there.

**Cost.** A member who has legitimately lost access to a workspace sees "not
found" rather than "you no longer have access", which is a worse error message.
The audit log records the real reason, and support can read it.

## ADR-0017 — Analytics visitors are keyed pseudonyms, derived server-side

**Amends ADR-0012**, which specified a "daily-rotating salted hash" but was
implemented as an unsalted `SHA-256(ip + user-agent)` at the edge.

**Decision.** The Worker sends a coarse per-request digest. The API derives the
stored value with `HMAC-SHA256` over a server-side secret plus the date, and
that is what is written.

**Why.** An unsalted hash of an address and a user agent is not a pseudonym.
The input space of IPv4 addresses and common user agents is small enough to
enumerate exhaustively on commodity hardware, so anyone holding the digests can
recover the addresses — which is precisely the property ADR-0012 claimed to
have.

Keying it removes the enumeration, because the attacker would also need the
secret. Deriving it in the API rather than at the edge means one process holds
that secret, and rotating it re-pseudonymises every visitor.

**Cost.** One more HMAC per event, on a path that already writes to Postgres.
Rotating the secret breaks continuity of the visitor dimension across the
rotation, which is the intended behaviour rather than a side effect.
